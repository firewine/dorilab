# v06 적용성·반증 평가 분석

## 결론

현재 e2는 현재 범위의 기록만 주면 action 12/12, 전체 계약 9/12를 통과했다. 같은 기술 주제의 다른 시험체·형상·run 기록을 함께 주면, 현재 기록의 위치에 따라 전체 계약이 4/12·1/12·2/12로 낮아졌다. 쉬운 사무 기록을 제외하는 이전 학습이 형상/시험 적용성의 일반적인 구분까지 이어졌다고 볼 근거는 없다.

이 분석은 업로드된 `comparison.json`과 `comparison_cases.jsonl`의 저장 점수·원출력을 대조한 것이다. 새 모델 추론이나 원문 논문 검증은 실행하지 않았다. 12개 시나리오는 6개 주제의 관련된 A/B 쌍이며 4위치는 독립 표본이 아니다. 기존 원문에서 새로 작성한 상황이지 새 시험 프로그램 holdout은 아니다.

## e2 결과

| 현재 범위 관측의 배치 | Action 정답 | 정확한 근거 선택 | 전체 계약 | 범위 밖 근거 인용 |
|---|---:|---:|---:|---:|
| clean: 현재 범위 기록만 | 12/12 | 12/12 | 9/12 | 0/12 |
| first: 처음 | 7/12 | 11/12 | 4/12 | 1/12 |
| middle: 중간 | 9/12 | 1/12 | 1/12 | 11/12 |
| last: 마지막 | 8/12 | 2/12 | 2/12 | 10/12 |

원입력의 모든 위치 조건을 통과한 사례/쌍은 e1과 e2 모두 0이다. e1 전체 계약은 clean/first/middle/last에서 8/4/0/1건이다. e2가 clean에서 좋아졌어도 혼합 기록의 적용성 처리가 충분히 안정된 것은 아니다.

## 오류는 근거 ID의 선택에만 국한되지 않는다

- AP06-02-B: clean에서는 NO_ACTION_REQUIRED이고 정답이다. first에서는 동일한 올바른 SF/OBS를 인용하면서 REQUEST_EVIDENCE로 바뀐다. middle/last에서는 action이 틀리고 인용도 범위 밖 관측으로 바뀐다.
- AP06-05-B: clean에서는 CHALLENGE로 맞히지만 first에서는 올바른 근거 ID를 그대로 인용하면서 NO_ACTION_REQUIRED로 잘못 수용한다.
- AP06-04-B: clean에서는 자료 요청 action과 근거가 맞지만 MODAL_INPUTS_MISSING 대신 PARAMETER_IDENTIFICATION_INSUFFICIENT를 쓴다. middle/last에서는 해당 범위의 관측을 다른 관측으로 교체한다.

따라서 출력에서 범위 밖 ID만 삭제하는 방식은 충분하지 않다. 이미 범위 밖 정보가 행동 선택에 영향을 준 사례가 관찰된다. 정확한 ID 인용은 올바른 의미 적용의 충분조건이 아니다.

## clean에서 남은 e2 오류 3개

| 사례 | 정답 reason | 모델 reason |
|---|---|---|
| AP06-01-B | MEASUREMENT_MAPPING_MISMATCH | BOUNDARY_CONDITION_UNRESOLVED |
| AP06-03-A | MODE_SELECTION_MISMATCH | PARAMETER_IDENTIFICATION_INSUFFICIENT |
| AP06-04-B | MODAL_INPUTS_MISSING | PARAMETER_IDENTIFICATION_INSUFFICIENT |

세 건 모두 action/근거 선택은 맞고 reason이 기준 라벨과 다르다. 이는 이번 후보 라벨과의 비교이며, 이 보고서가 자동으로 이유 분류를 수정하거나 대체 정답을 추가한 것은 아니다.

## 설계 제안: 명시적 적용 범위의 일치 검사는 입력 전처리에 분리

v06의 질문에는 unit/configuration/run이 모두 일치하는 기록만 근거로 사용할 수 있고, 다른 기록의 동등성·재사용 근거는 없다고 명시되어 있다. 따라서 이 특정 정책은 정답을 보고 고르는 것이 아니라 입력 필드 세 개를 비교하는 코드로 실행할 수 있다.

제안 경로:

질문·승인된 범위 → 범위 게이트 → 현재 범위의 기록으로 문맥 구성 → LLM의 action/reason 선택 → 출력 schema/허용 근거 ID 검사 → 사람/실행 규칙에 따른 다음 단계

범위 밖 기록은 삭제하지 않고 원본과 제외 이력을 보존한다. 범위가 없거나 읽히지 않으면 중단하고 확인을 요구한다. 일치하는 기록이 여러 개라면 모두 남기며 그 안의 모순·관련성은 별도 검토한다. 이 단계가 물리적 유효성이나 결과 적합성을 승인하는 것은 아니다.

실제 운영에서는 검색 본문이 자기 주장하는 문자열이 아니라 검증된 구조화 메타데이터를 사용해야 한다. 전후 비교, 이전 시험의 재사용, 형상 동등성 검토 같은 업무에서는 다른 정책이 필요하다. v06용 exact-match 게이트를 그런 업무에 그대로 적용하지 않는다.

## 제공 코드가 하는 일과 하지 않는 일

`scope_gate_v07.py`의 선택 함수는 `role`과 `packet`만 받는다. `expected`, `acceptable_answers`, `authoring.expected_scope_record`는 선택에 전달하지 않는다. 현재 v06 입력의 기계적 scope 헤더만 엄격하게 읽는다.

`audit`는 기존 manifest/검토/입력 hash를 확인하고, 범위 게이트를 통과시킨 각 입력이 이미 평가한 clean의 role+packet과 같은지 확인한다. 구조와 JSON key 순서를 보존한 직렬화를 모두 비교한다. 이 단계는 tokenizer나 모델을 실행하지 않는다.

일치한다면 이미 관찰한 clean 점수(e2 action12/12·전체9/12)가 어떤 정리된 입력에서 나온 것인지 연결할 수 있다. **이를 새 게이트 통합 모델을 실행해 얻은 점수나 raw 모델 능력 향상으로 기록하지 않는다.** 실제 메타데이터 취득·정합성 검증과 운영 연결은 아직 별도 작업이다.

출력은 새 `data/scope_gate_v07/` 폴더에만 쓴다. 학습/평가 코드·가중치·정답·승인·기존 점수는 바꾸지 않는다. 원입력 모델 평가는 그대로 보존하고, 시스템 전처리의 이점과 분리한다.

## 별도 발견: 중복 JSON key 1건

e1 / AP06-05-B / middle의 raw_output은 `evidence_refs` key가 두 번 나온다. 저장된 parsed에는 마지막 값만 남아 있다. 배열 내부의 중복 ID와는 다른 문제다. 이 사례는 원래도 전체 실패이므로 이 플래그는 현재 전체 통과 수를 높이거나 바꾸지 않는다. 기존 점수는 유지하고, 실제 실행용 출력 validator에는 중복 key 거부를 별도로 추가할 근거로 기록한다.

## 다음 작업

1. e1/e2 및 v06 원입력 결과를 보존한다. 같은 사례로 epoch를 더 늘리지 않는다.
2. `python scope_gate_v07.py audit`로 gold 없이 구현한 입력 전처리와 기존 clean의 동등성을 확인한다. 새 GPU 추론은 필요 없다.
3. 제품 경로에는 명시적인 범위 선택을 모델 앞단에 두고, 필요한 판단·동등성 예외·상충 근거 해석은 별도 모델/승인 단계로 남긴다.
4. 후속 모델 규모 비교에서도 raw 모델과 게이트를 포함한 시스템 점수를 구분한다. 신규 시험 프로그램과 검토된 메타데이터 오류/예외 조건은 따로 평가한다.

## 제작 검증 범위

CPU 테스트28개와 임시 프로젝트의 전체 audit 실행을 통과했다. 정상 순서 변경, 범위 누락, no-match, 동일 범위의 상충 관측 보존, 잘못된 정책, 데이터 변조, 중복 key, 결과 overwrite 방지 등을 검사했다.

실제 사용자 PC의 v06 입력 JSONL/manifest/검토 파일은 이번 업로드에 포함되지 않았다. 그러므로 **사용자 원입력에 대한 gate 동등성 확인은 로컬 audit가 수행**한다. 업로드된 실제 결과 파일은 Python으로 재집계했고 저장 요약과 맞는지 확인했다. GPU 학습·추론은 실행하지 않았다.
